## 1. 维护与读取规则

**本文件属于受保护规范，不享有 milestones.md 的日常更新例外。新增条目、修改状态或内容、删除、重命名、移动本文件，均须事先获得人工对具体变更的明确批准。** 不能因“只是补充事实”“记录一个建议”或“便于 agent 理解”就自行追加。当前用户已授权首次创建本文件，不代表初始提案已全部获准，也不构成以后随意修改的长期授权。

普通实现选择在已批准职责与契约内由对应 agent 自主完成，不需要每次请求批准或写入本文件。实际数据源、字典条目、推荐规则版本、依赖锁定和测试结果，按各自规范记录在对应产物、代码或 PR；日常进度和暂未获准固化的建议记在 milestones.md 的相关任务记录中。只有影响长期共享约定、解释重要取舍或确需改变受保护规范时，才整理具体决策文本并请求相应批准。

人工批准已经清楚覆盖某项决定及对应规范同步时，agent 直接完成获准范围，不额外要求用户重复说文件名、决策编号或填写表单。授权范围不清或与既有要求冲突时，说明具体差异并继续其他可独立工作，不能把局部不确定变成全项目停工。

读取时同时区分三个问题：条目是否已批准，批准范围是什么，相关实现和规范是否已经同步。**accepted 不等于已安装、已采集、已提交、已合并或验证通过。** 后者只由实际产物与验证证明，不通过本文件的状态推断。

本文件只追溯已有决定，不优先于用户当前明确指示，也不替代详细契约。发现台账、规范与实现冲突时，列出真实差异，按已有批准范围同步；不能选择最方便的版本、凭新建条目覆盖旧契约，或用实现已经写完倒推需求已变更。规范头部仍写草案时，应核对实际验收范围，不能忽略可核实的既有批准；必要状态同步仍按受保护文件规则处理。

## 2. 状态、证据与替代关系

| 状态 | 含义与执行边界 |
| --- | --- |
| `accepted` | 有可核实的人工确认或对具体方案的验收，仅在其范围内生效；不代表实施完成。 |
| `proposed` | 已有明确方案，但批准依据尚未取得或尚待核对；不能据此变更规范、扩展职责或提前执行受限操作。 |
| `open` | 尚无确定结论，需按既有权限实践或取得必要决定；不表示所有相关工作都要等待人工。 |
| `rejected` | 人工明确否决过的方案，保留理由与证据，不等同于某个从未选过的方案。 |
| `superseded` | 原已批准决定被新的已批准条目替代；保留原记录并指向新条目，不能无依据重新启用。 |

条目 ID 使用递增的 DEC-NNN，已有 ID 不重新编号或复用。状态与批准依据应相互对应；不能把 agent 建议、测试通过、PR 建立、自动审查或另一 agent 同意当作人工批准。仅验收本台账的记录准确性，不自动将 proposed/open 变成 accepted；用户明确批准具体提案或列明的全部方案时，按真实覆盖范围处理，不要求再走一轮重复审批。

批准依据可引用当前可核实的用户原话、已验收文档及相应对话，或实际 PR/审查记录。缺少链接就说明可核实的表述与位置，不编造网址、审批编号、姓名、签字、批准日期或会议记录；缺少链接也不意味着必须让用户重验已批准内容。

出现替代决定时，先说明原 ID、原因、受影响规范、实现迁移与验证方式；取得具体批准后，以新 ID 记录，将旧条目标为 superseded 并互相链接，按范围同步规范和实现。未批准前保留原决定有效，不能删掉旧记录掩盖变更过程。普通实现修复不因此被要求新增决策条目。

## 4. 已确认要求与已验收方案

### DEC-001：规范保护、agent 读者与进度例外

- 依据：用户明确“这些文件是不应该被其他 agent 随意修改的，除了 milestones.md”，规范修改必须人工批准；随后明确文档供 agent 使用，成员可能只说“我会完成 B 的任务”。详见 project.md 与已验收 roles.md。
- 决定：规范内容的变更先获具体批准，只有 milestones.md 可按规则维护日常进度；agent 承担阅读、任务定位、检查与交接，不把这些步骤转交成员手工完成。CLAUDE.md 按用户要求保留，并只引入 AGENTS.md。
- 原因与边界：保持共同要求稳定，并避免两套 agent 规则漂移。进度维护例外不允许重分配职责、放宽验收或取消必用技术；普通代码实现不套用规范修改审批。
- 落实入口：AGENTS、README、CLAUDE、配置及 PR 模板入口已按用户指定创建；CLAUDE 仅引入共同规则，交付进度见 M0。本条不代表允许任意改写这些入口。

### DEC-002：数据范围与时间口径

- 依据：用户补充确认“数据覆盖全国，如果可行可以覆盖全世界；截止 2026.10 月”，且没有最低数据量要求，需要尽可能多收集。权威范围见 project.md 第 2.1 节。
- 决定：全国是基础覆盖目标，全球是可行时扩展；以去重后有效数据和实际覆盖说明成果。2026-10 是数据时间截止月，不是项目交付截止日。
- 原因与边界：目标范围不能冒充已经覆盖的事实；采集时间与来源发布时间分别记录，不获取或声称尚未发布的信息，不用重复记录凑量。
- 落实入口：A 的来源与批次元数据、质量说明；实际数量和地区缺口随数据记录，不固化在本文件。

### DEC-003：必用的大数据处理环节

- 依据：用户明确“Hadoop/HDFS、MapReduce 必须使用”；选题分工与 project.md 同时要求 Spark SQL 分析。架构与环境方案后续已验收。

- 原因与边界：展示真实的数据处理链路。K-Means 只在特征合适时作为可选增强，不能替代任何必用环节；单机演示不能描述成多机器性能验证。
- 落实入口：M2 的真实小样本闭环与 M3 的所选数据批次运行；实际路径、任务与统计口径以环境和数据契约为准。

### DEC-004：离线处理与在线查询分离

- 依据：用户明确验收 architecture.md 后继续下一份文件；该文档规定单仓库、离线批次与在线网页两条流程。
- 决定：采集、清洗、HDFS、MapReduce/Spark SQL 离线执行，校验后的标准数据和统计进入 MySQL，Flask 为 Vue 页面提供查询与推荐；网页请求不启动采集或大数据作业。
- 原因与边界：三人可按稳定产物接入，网页无需等待每次批处理；最小版本不新增常驻调度平台或其他分布式服务。更新暂停接口、校验后发布并保留恢复能力，具体步骤查原规范。
- 落实入口：architecture.md、environment.md，以及 M2、M4 的接入和恢复验证；本条不证明系统已运行。

### DEC-005：标准批次、质量语义与统计对账

- 依据：用户验收 data-contract.md 后指定继续 API 契约；版本 1.0 是已验收的共享数据约定。

### DEC-006：API v1 与内部模块调用

- 依据：用户验收 api-contract.md 后指定继续环境文档；该文档明确 HTTP 与内部函数的输入输出和错误边界。

### DEC-007：角色识别与三人边界

- 权限与下一步：A 整理来源与类型字典，B 反馈统计和推荐可用性；真实价格政策依契约取得所需批准并登记。普通字典整理不改变既定结构；需改契约或缩减功能时先展示具体范围并获准，见 M3-A02。
- 不得推定：未知等于免费、区间/起步价可直接用于预算、测试政策是生产默认，或 pending_policy 已证明真实价格功能完成。政策缺失不阻断普通查询和有效地区偏好，但不能据此取消预算需求。

### DEC-013：推荐最终排序与验证案例

- 依据：用户暂未确定最终排序、权重和案例，已验收接口将实际规则设计与说明留给 B。
- 待落实：在数据真实可用的前提下，选择、实现和验证可解释排序，登记实际 rule_version、理由与必要案例，不提前填权重或效果指标。
- 权限与下一步：B 可在已批准硬约束与调用契约内自主迭代普通算法实现，不为每次调参请求人工批准或更新本文件；记录于模块、验证、PR 和 M3-B03。改变预算资格、偏好语义或接口时才触发相应规范审批。
- 不得推定：规则分数等于准确率、满意度或经过训练的预测；不能只读取列表当前页作为完整候选，也不能无结果时静默放宽条件。

### DEC-014：项目日期与补充课程要求

- 依据：用户尚未确定截止日和阶段日期，未提供额外的最低数据量、必交材料或评分要求。
- 待决定：真实的交付时间与后续实际收到的课程要求；没有指定日期时继续按依赖推进。
- 权限与下一步：取得真实信息后由 agent 核对影响，更新允许维护的进度；改变受保护要求时按具体批准同步。无需成员先填写一份计划表才可开始已授权任务。
- 不得推定：2026-10 是项目截止日，或自行增加数据条数、集群节点、准确率、响应时间作为课程硬指标。

### DEC-015：公开分发细节

- 依据：项目使用 GitHub 协作，但用户尚未确定代码与数据的完整公开分发方案；project.md 已明确秘密与未确认第三方数据不能进入公开仓库。
- 待决定：代码许可、可公开样本与全量数据的不同处理方式、受限数据复现入口，以及地图/图片等第三方资源的实际使用和分发边界；不默认选择某个许可证。
- 权限与下一步：A 整理数据来源和允许范围，B/C 整理自身产物与页面资源，agent 在实际发布前准备具体可审查方案；可继续不依赖公开分发决定的已授权实现。
- 不得推定：代码 PR 授权同时覆盖上传数据库备份、全部原始页面或第三方资源；不通过 Git LFS、Release 或网盘绕过未确定的数据发布范围。

## 7. 后续条目格式与变更检查

取得相应写入授权后，agent 自动整理下列信息，不要求成员手工填写。简单条目可合并字段，但不能缺少批准边界或把未定项写成结论。下面是格式说明，不是一个真实决定，也不预设批准状态。

```text
DEC-NNN：具体问题或选择
状态：proposed / open / accepted / rejected / superseded
问题与约束：为什么需要这个决定，已有规范要求是什么。
决定或候选：本次实际结论；未知项和候选明确分开。
理由与代价：有依据的取舍、未采用方案及必要限制；没有比较过就不编造。
影响与权威规范：具体文件、模块和职责；本条不复制完整契约。
批准依据：可核实表述或实际记录及授权范围；未取得则明确写未取得。
实施与同步：需要修改的规范、实现、迁移和验证，实际状态引用里程碑证据。
替代关系：如有，列出被替代/替代本条的真实 ID；没有则写无。
```

获准变更时，同时检查索引与正文状态、批准证据、替代关系和受影响规范的一致性。尚未执行的验证不能预填成功；实际困难不能通过修改决策理由或降低验收来掩盖。批准只覆盖明确范围，不扩展为公开数据、购买服务、发送外部消息或合并 main 的通用权限。

本文件记录规范选择与批准依据，不自行触发采集、安装、开发或发布。规范与配套入口已建立，当前进度由 milestones.md 维护；统一文档交付和后续实施按用户授权及实际阶段执行。
