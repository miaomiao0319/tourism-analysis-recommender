# Git 协作、提交与 PR 规范

- 文档状态：已验收基线；实际提交与交付状态见 milestones.md。
- 主要读者：承担 A/B/C 任务的开发 agent。
- 依据：[项目要求](project.md)、[系统架构](architecture.md)、[角色分工](roles.md)、[环境约定](environment.md)；字段和调用分别遵循[数据契约](data-contract.md)、[接口契约](api-contract.md)。

agent 自行检查仓库、选择分支、整理提交、验证、推送任务分支并维护 PR，不要求成员本人先读 Git 文档、手工填写 PR 模板或逐条执行命令。角色由用户明确指示，不根据分支名、Git 作者或 GitHub 账号猜测。

**修改、删除、重命名或移动本文件，必须事先获得人工对具体变更的明确批准。** 本文首次编写只建立规范，不表示相关 Git 操作已经执行。实际执行范围由用户当前指示、项目阶段和下述约定共同确定；命令示例不是立即执行指令。

## 1. 阶段、权限与保护边界

| 场景 | agent 应如何执行 |
| --- | --- |
| 文档准备阶段 | 按用户指定逐份创建、等待验收；保留本地工作，全部文档完成后统一提交一次文档 PR，不为每份文件分别发 PR。 |
| 已进入实现阶段，用户指定角色或任务 | 在已批准职责与当前阶段内完成必要实现、检查、任务分支提交与推送、创建或更新 Draft PR；不为每次普通提交、推送重复请求确认。用户明确要求只在本地工作时，以其限制为准。 |
| 修改受保护文件或改变需求、职责、数据/API/环境约定 | 先展示具体问题、拟改内容和影响，获得人工明确批准后再修改；不能先改好再用 PR 请求追认。 |
| 合并进入 main | 由有权限的人工维护者执行，或在人工明确授权 agent 合并具体 PR 后执行。创建 PR、代码自测通过和文档验收不自动等于合并授权。 |
| 首次建立空仓库基准 | 仅按第 3 节的初始化例外处理；不能以初始化名义把文档或实现直接推入 main。 |

受保护范围包括 README.md、AGENTS.md、CLAUDE.md、`docx/` 内规范文档，以及承担共同约定作用的 .env.example、.gitignore、PR 模板等入口。路径尚未创建时仍按该边界处理；新增替代规范、子目录 agent 规则或另一份契约不能绕过现有规则。

唯一日常维护例外是 `docx/milestones.md`：agent 可按其格式更新自己任务的真实进度、证据与阻塞，不得借此改范围、负责人、验收标准或审批规则。代码内的必要注释、测试和运行入口说明不自动视为规范文档；新增独立文档或修改共享约定时先判断是否属于受保护范围。

人工授权应能对应具体文件、变更和范围。用户在对话中明确批准的内容可作为依据，agent 在 PR 说明批准内容与可核实位置；不要求用户重复填表或再到另一个界面批准一次。另一 agent 的同意、自动审查、提出建议、旧任务的泛化授权均不能替代这项批准；没有可分享的对话链接时如实说明，不编造审批编号。

接到已明确授权的修改时直接执行，不因本文件再重复询问。越出授权范围的部分先保留不动，说明差异并等待决定；可继续独立的已授权工作。PR 只展示已获准的规范修改，不夹带未获准的“顺手修正”。

## 2. 仓库、分支与工作区

唯一项目仓库为 [miaomiao0319/tourism-analysis-recommender](https://github.com/miaomiao0319/tourism-analysis-recommender)，日常集成基准为 main。不增加 develop、长期 A/B/C 分支或三个互相复制代码的仓库。

| 分支 | 命名及用途 |
| --- | --- |
| main | 已通过相应检查并获准合并的共享成果；保持能够按当前阶段复现，不把构造样本通过写成真实系统完成。 |
| 普通任务分支 | `<type>/<role>-<topic>`；type 使用 feat、fix、refactor、test、chore、docs，role 为 a、b、c，topic 用简短英文小写及连字符。 |
| 首批文档分支 | `docs/project-foundation`，承载当前全部已验收文档和明确授权的配套入口。 |

例如 `feat/a-source-catalog`、`feat/b-mapreduce-counts`、`feat/c-attraction-search`。一个分支对应一项可独立检查的能力或问题；一个 PR 可包含完成该能力所需的多个文件，普通任务不因跨两个目录就拆成无法独立使用的碎片 PR。分支名只标识工作，不授予角色或权限。

各成员通常在自己的 clone 工作。多个 agent 同机并行时，使用各自独立 checkout 或必要的独立 worktree，避免在同一个工作目录同时改分支、索引和共享文件。已有适合的任务工作区时优先复用，不为小修改强制创建 worktree；未建立首个提交时不套用依赖已有提交的 worktree 流程。

agent 开工先做只读检查，命令从实际仓库根目录执行；不要在课程资料父目录误初始化另一份仓库：

```text
git status --short --branch
git branch --show-current
git remote -v
git diff
git diff --cached
```

核对实际 origin 对应上述仓库。HTTPS 与 SSH 地址可指向同一仓库，不能因认证失败就改成别人的仓库或自动创建 fork。Git 身份沿用成员已配置的真实身份；缺失且确实阻止提交时再请求必要信息，不捏造姓名邮箱，也不擅自修改全局 Git 配置。

有未提交或已暂存内容时，先识别来源与任务范围；当前会话已授权的自己的工作可以继续。其他人留下的修改、无法确认归属的文件或暂存内容不得自动提交、丢弃、藏入 stash 或带到另一分支。必要时保留当前目录、另用隔离工作区继续任务，不能先清理再解释。

## 3. 第一次文档 PR 与空仓库初始化

“No commits yet”只说明本地尚无提交，不证明 GitHub 远端为空。汇总 PR 阶段先读取远端默认分支和引用，再选择路径；文档准备期间无需为了写下一份文件提前造提交或推送。

| 实际状态 | 处理方式 |
| --- | --- |
| 远端已有 main 或其他历史 | 保留现有历史，取得正确基准，基于它建立文档分支并放入已验收内容。不用 force、重新 init 或删除远端分支修复本地未同步问题。 |
| 远端已有历史但默认分支不是 main | 说明与本文的差异；不能擅自改默认分支、创建替代 main 或合并无关历史。先准备保留历史的具体接入方案，影响共享基准时由人工决定。 |
| 远端完全无提交，本地也无提交 | 等全部文档完成、已到获授权的汇总 PR 阶段后，先建立一个只含空根提交的 main 作为比较基准，再从它创建 docs/project-foundation。全部文档放在文档分支，通过唯一一次文档 PR 提交。 |
| 远端为空但本地已有提交 | 保留既有提交与工作，不能套用空根流程或重写历史；基于真实状态说明可保留成果的初始化方案，不能直接把整批文档推到 main 来跳过 PR。 |

空根提交是“禁止直接推送 main”的唯一初始化例外，必须同时满足：真实远端为空、本地无提交、全部文档准备完成、当前用户已授权执行汇总 PR，并且没有其他人正在初始化同一仓库。它只建立 PR 基准，不包含 README、文档、样本或实现。已有充分授权时不再重复询问；单份规范的创建或验收不触发该执行阶段。

初始化前核对分支与索引确实为空。`git commit --allow-empty` 仍会包含已暂存文件，不能把它误认为自动保证空提交；有不明暂存内容就停止该步骤，不自动取消别人的暂存。推送前后检查远端，若已被他人建立则保留其历史并重新评估，不强制覆盖。不能在受保护远端规则阻止初始化时绕过规则。

已有基准后，agent 在 docs/project-foundation 明确暂存所有本次获准的文档与配套文件，检查差异、链接与审批范围，形成一次汇总文档 PR。根目录说明、规则、模板等尚未创建或验收时，不能因为已有部分文档就宣称全部完成。

## 4. 日常开发与同步流程

进入正常实现阶段且 origin/main 已存在后，按以下顺序执行：

1. 识别角色、任务、当前阶段和依赖；检查工作区、已有分支和同任务 PR，复用尚未完成的同一任务，不重复开分支或 PR。
2. 每次开始或恢复开发（新会话、继续已有任务或开始新任务），先 `git fetch origin` 获取最新远端状态，再按下方规则将所需更新整合到实际工作分支；fetch 只更新远端跟踪引用，不能单凭命令成功就声称本地代码已经同步。
3. 按角色边界完成最小必要实现及检查。依赖未就绪时可使用明确标记的测试替身，但不能把它记为真实联调通过。
4. 使用明确文件路径暂存，核对暂存差异及敏感内容，再提交。必要修复与相关测试同批交付，不夹带另一个任务。
5. 推送前再次 `git fetch origin`，核对对应远端任务分支与 origin/main；有更新时按下方规则整合到自己的任务分支，按第 7 节解决冲突，并重跑受影响检查。
6. 推送该任务分支，创建或更新指向 main 的同一 Draft PR，提供真实检查、依赖和交接信息；达到第 6 节条件后可标记 Ready for review。

开工同步由 agent 执行，成员不必另外手工拉取。完成第 2 节的工作区检查后，在工作区干净、目标分支归属明确且没有未完成的合并等操作时整合；自己已获授权任务的改动可先核对并正常提交，不能为同步自动提交他人或来源不明的内容，也不自动 stash、reset 或清理未跟踪文件。

| 开工场景 | 同步方式 |
| --- | --- |
| 新任务 | 从本次 fetch 得到的 origin/main 建立新任务分支；不要从旧的本地 main 或其他人的未完成分支直接开工。 |
| 继续已有任务 | 复用原任务分支。若对应 origin/任务分支存在，先比较双方提交：仅远端领先时用 `git merge --ff-only origin/<任务分支>`；本地已包含远端则无需重复整合；双方分叉时先查看新增内容，确认同属本任务后普通 merge 保留双方历史，按第 7 节处理冲突。远端分支不存在时核实是尚未推送、已合并或被删除，不自动丢弃本地任务或重新创建已结束的任务。 |
| 任务分支已同步远端自身更新 | 再核对本次获取的 origin/main；有尚未纳入的主线提交时，在自己的任务分支执行 `git merge origin/main`。新任务刚从该主线建立时无需重复 merge。 |

整合后重新检查工作区与提交关系，读取更新后的 AGENTS.md、相关规范和 milestones.md，再开始实现；有冲突时先解决并验证，不在冲突未解决的状态下继续开发。受保护规范出现实质冲突时遵守第 7 节及已有批准范围，不自行挑选一方覆盖。

网络或认证失败、远端基准缺失、归属不明等导致无法确认同步完成时，说明具体缺口，不宣称“已拉取最新代码”；记录后继续不依赖该更新的独立工作，相关实现和交付前补齐同步。本节不要求初始文档草稿阶段提前建提交、切分支或整合远端，首次文档交付仍按第 3 节处理。

以下是 A 的一个新任务示例，不是要求三个角色都使用同一分支；仅在前述前提满足时由 agent 执行：

```text
git fetch origin
git switch --create feat/a-source-catalog origin/main
```

后续同步在**自己的任务分支**执行 `git merge origin/main`，不是把任务分支合入 main。不使用含糊的 git pull 去同时猜远端、合并方式和冲突策略；不 rebase 已发布的共享任务分支，不为整理历史强推。Git 合并行为参考[官方 merge 文档](https://git-scm.com/docs/git-merge)。

依赖另一个尚未合并的 PR 时，优先继续不依赖部分，或在当前 Draft PR 中写清依赖的 PR、提交与缺口。确需基于其提交开发，先通过已授权协作方式对齐，明确实际基点；不得把上游提交冒称自己的交付，不把临时依赖分支悄悄当成长期集成分支。上游合并后再与 main 对齐、核对最终 diff 并验证，不将“依赖未合并”标为集成完成。

不自动合并、cherry-pick 或重写他人的未完成分支来绕过交接。跨模块改动遵循 roles.md；必要说明写在 PR 和交接记录中。跨会话消息、点名请求审查等动作只在用户已授权的协作渠道执行，不能声称已通知实际未联系的人或 agent。

## 5. 提交内容、暂存与数据公开边界

提交标题采用 `type(scope): 简明结果`，type 与分支类型同类，scope 选择 crawler、cleaning、db、mapreduce、spark、recommend、api、web、env、docs 等实际模块。说明具体能力或修复，不使用“更新”“最终版”“fix all”替代内容；不要求英文长描述或每个微小编辑都单独提交。

例如 `feat(crawler): 新增公开景区名录解析`、`fix(recommend): 保留零预算筛选条件`、`docs(project): 建立项目协作规范`。提交作者沿用真实 Git 身份，不添加虚构作者、审批者或来源信息。

| 通常应提交 | 默认不提交 |
| --- | --- |
| 本任务源码、必要测试、数据库结构及导入代码。 | .env、密码、令牌、含凭证的连接串、私钥及个人账号配置。 |
| pyproject.toml、uv.lock、.python-version、package.json、package-lock.json、.nvmrc 及脱敏的共享版本记录。 | .venv、node_modules、dist、.runtime、安装包、Spark/Hadoop 二进制、数据库文件、HDFS 持久目录。 |
| 本次已获准创建或修改的规范、配置示例与模板。 | 抓取的整站页面、原始/全量标准数据、全量分析输出、数据库备份、含私人路径或敏感内容的日志。 |
| 已明确适合公开且可追溯的最小样本及必要元数据，或清楚标记的构造测试样本。 | 未确认再分发条件的数据、地图、图片、评论和其他第三方资源；不能因为网页可访问就提交。 |

数据的具体公开分发方案仍未确定。文件体积小、目录名叫 samples、data_kind=real/test 或已经被 .gitignore 忽略，都不能独立证明适合公开；来源与用途按项目要求和数据契约判断。数据下载、校验和重建入口通常比上传整套数据更适合复现，不自行启用 Git LFS、Release 附件或外部网盘替代未获准的数据发布。

样本需要能支撑必要检查，但不能将未经批准的真实票价口径当作测试政策推广到真实数据。构造样本标记 test，样本、字典和证据必须一致，不能为了缩小差异只上传无法复现的半份快照。

暂存前查看工作区；按明确路径执行 git add，不默认 `git add .` 或 `git add -A` 把他人文件与大数据产物一起加入。检查暂存内容时至少执行：

```text
git diff --cached --name-status
git diff --cached
git diff --cached --check
```

同时检查将推送的整个任务分支差异及本分支新增历史，不能只看最后一次提交。.gitignore 不会取消已跟踪文件或清除旧提交中的秘密。若敏感内容已提交或推送，立即停止继续传播并说明受影响位置；涉及凭证失效和历史清理时按具体授权处理，不自行强推共享历史，也不能仅删除当前文件后宣称已解决。

依赖声明与对应锁文件一起提交，按 environment.md 的管理工具更新；禁止手工拼接 uv.lock/package-lock.json 凑合冲突。配置缺失不能用硬编码本机路径或密码补齐。受保护的 .gitignore 或 .env.example 需要变更时，先取得具体批准，不为通过检查偷偷修改。

## 6. 推送、PR 与检查证据

推送前确认当前分支、目标仓库、提交范围、受保护文件审批和必要检查。只推本任务分支；不使用 `--all`、`--mirror`、自动推标签或强制推送选项。默认使用新增提交修复已发布分支，避免覆盖他人提交。[Git push 文档](https://git-scm.com/docs/git-push)说明不同推送选项的作用；工具允许操作不等于本项目授权使用。

同一任务优先更新已有 PR。创建新 PR 时明确指定仓库、base=main 与实际 head，默认 Draft；不让 CLI 自动猜分支、fork 或把创建 PR 和合并 main 合成一个动作。PR 内容由 agent 根据最终 diff 和真实验证自动编写，PR 模板只是相同信息的入口，不要求成员本人填写。

PR 至少清楚说明以下信息，简单任务可用短段落，不机械扩成长报告：

- 解决什么具体问题，完成后产生什么行为或产物，涉及哪个角色与模块。
- 是否影响共享字段、接口、环境、数据库结构或受保护文件；有规范变更时说明对应人工批准范围。
- 实际执行的检查命令、结果与必要证据；未执行项、原因、仍存在的限制和依赖分开说明。
- 数据处理任务对应的 batch_id、data_kind、引擎与可共享证据位置；构造样本通过不等于真实数据通过。
- 接收方 agent 的入口与下一步接入工作。存在未合并依赖或测试替身时显式标记。

标题和说明随最终实现更新，不沿用已放弃方案的描述。PR 不要求附全量日志或截图；仅在解释页面行为或运行结果确有帮助时附脱敏证据，不上传原始隐私数据。

GitHub CLI 示例：agent 先将完整 PR 正文写入本机 `.runtime/pr-body.md`，再引用文件，避免多行文本被 Shell 展开。文件不存在或平台无 CLI 时，不把示例当作已创建结果；使用当前已授权可用的仓库工具完成同一操作。

```text
git push --set-upstream origin feat/a-source-catalog
gh pr create --repo miaomiao0319/tourism-analysis-recommender --base main --head feat/a-source-catalog --draft --title "feat(crawler): 新增公开景区名录解析" --body-file .runtime/pr-body.md
```

选项与正文文件用法参考 [gh pr create 官方说明](https://cli.github.com/manual/gh_pr_create)。命令成功后读取真实 PR URL，能关联当前任务附件时关联该 PR；后续推送更新同一 PR，不为每次修复新建 PR。认证或网络失败时保留本地提交，说明尚未推送或创建，继续可独立工作；不伪造 URL，也不声称已通知其他成员。

验证按实际变更选择，不因为没有 CI 就跳过，也不为文档措辞修改编造数据库和集群测试。检查记录需区分：静态检查、构造样本自测、真实小样本处理、模块接入和完整系统演示。命令存在、依赖安装成功、health 成功，均不能替代后续层次的成功。

只有当前 PR 的承诺范围已完成、必要检查通过、依赖和限制如实说明、没有未获准规范修改或未解决冲突时，agent 才可标记 Ready for review。外部条件阻止必需验证时保留 Draft，说明缺口；可继续提交进展，不将阻塞写成通过。并非每个 PR 都要跑全系统，但改变契约、导入、金额/预算判断等逻辑需有针对性的边界检查。

## 7. 冲突、共享文件与失败恢复

更新基准或合并前确保工作区可安全恢复，保留本次任务边界。冲突不能通过整文件选 ours/theirs、清空文件或接受最新时间戳自动解决，应逐段判断双方意图及契约；解决后检查合并结果而非仅删除冲突标记。

| 冲突类型 | agent 的处理原则 |
| --- | --- |
| 自己模块的普通代码 | 保留双方有效变更，完成最小修复并验证；涉及其他角色模块时按已有协作权限对齐，不重写整块模块。 |
| 数据/API/环境或角色约定 | 保留已经获准的上游规范；下游实现适配。需要改变最终含义时先取得具体人工批准，不能用冲突解决提交偷改规范。 |
| 已批准规范的机械合并 | 可以保留双方已批准内容、消除同一修改的冲突标记；若两项批准互相矛盾或需要新增语义，暂停该部分并说明差异，不自行决定新规则。 |
| uv.lock / package-lock.json | 先解决依赖声明及已批准版本要求，再用对应工具重新生成，检查非预期依赖漂移并运行相关检查。不能只选一方锁文件造成声明失配。 |
| milestones.md | 按任务条目保留各角色真实进展、证据和阻塞，遵循其格式，不整文件覆盖。自测通过与已接入等不同状态不能合并成虚假完成。 |
| 已发布标准快照、字典和计算产物 | 不在 Git 冲突中拼接两批数据或原地改已发布批次，按数据契约重新产生合法批次与证据。 |

解决冲突后检查 git status、差异、未合并项和冲突标记，重新运行受影响验证，再明确暂存并完成合并提交。自动重新生成的锁文件、格式化结果和进度合并也要检查，不能直接全部暂存。

发现任务分支远端被他人更新时，先 fetch 并查看新增提交；确认属于同一任务后在本地合并、验证再推送，不用 force 或 force-with-lease“抢回”分支。无法确认变更归属时保留双方历史，说明具体差异并继续其他可独立工作。

需要取消刚才的合并时，可在确认不会损失当前已有工作的前提下使用 merge --abort；它不是任意未提交修改的备份工具。禁止将 reset --hard、clean -fd、强制 checkout/restore、删除工作目录、批量 stash 或关闭检查钩子作为常规冲突处理。确需会丢失数据或改写共享历史的特殊恢复时，先保全成果、展示具体影响并取得明确授权。

## 8. 审查、合并与任务收尾

agent 完成自查并修复发现的问题；其他角色 agent 可在已授权协作范围提供审查或接入反馈，不能因此修改他人整个分支，也不能代替人工授予规范变更和合并权限。没有配置实际 CI、规则集或 CODEOWNERS 时，不能宣称 GitHub 已强制实施这些规则。

main 的仓库保护宜要求通过 PR 集成、限制强推，并使用项目实际存在的检查项；设置调整由有权限的维护者授权后实施，不虚构不存在的检查名称或阻止首个空基准建立。若仓库保护策略与本文件冲突，说明真实限制并请求具体决定，不尝试绕过。保护能力及适用条件参见 [GitHub 受保护分支说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。

拟合并 PR 前，核对最新 head、base 与最终差异、实际检查及人工授权。批准后新增了实质修改时重新验证；原批准未覆盖的规范变化先补充批准，不能沿用旧结论。遇到实际服务端审查或保护要求仍应满足，不能以“对话批准过”绕过技术限制。

人工明确授权 agent 合并某个 PR 后，agent 可执行并核实结果；默认采用 squash merge，让一个任务形成一个 main 提交，PR 内保留迭代检查记录。仓库未提供 squash 或存在其他明确约定时说明差异，不擅自改设置。没有合并授权时交付可审查 PR 后停止合并动作，不能启动自动合并。

合并后由实际执行收尾的 agent 记录合并提交、PR 和接入结果，更新 milestones.md 中对应状态。代码已合并不自动代表集群运行、真实数据分析、系统联调或整个里程碑通过；以相应验证证据判断。

确认远端结果后，其他成员 agent 在自己的工作区 fetch 并同步主线。任务分支仅在已合并、没有依赖它的工作、没有未保存成果时清理，按当前授权和工具规则执行；不删除他人的分支或工作区。发现已合并变更有问题时，优先通过修复 PR；回退需要按实际风险和授权处理，保持 main 历史可追溯，不重置或强推主线。

## 9. agent 交付时的最小汇报

每次汇报包含实际完成内容、检查与限制、当前分支/提交/PR 的真实状态，以及“下一步计划”。本地文件完成、已提交、已推送、PR 已创建、已合并和已接入是不同状态，不互相替代。

没有 PR 就明确说尚未创建；没有运行就说明未运行。后续进度写入 milestones.md，重要取舍按获准的 decisions.md 维护规则处理，不在本文件追加日记、不另建一份进度账。

本文件只规定 Git 协作与提交边界，不重新分配 Hadoop/MapReduce 职责、不改变数据或 API 格式，也不替代 README、AGENTS、CLAUDE、里程碑与 PR 模板各自的作用。初始入口均已形成，实际交付与后续变更按用户授权和里程碑执行。
