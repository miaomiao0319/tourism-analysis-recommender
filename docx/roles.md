# 三人分工、代码归属与交接要求

- 文档状态：已验收基线；实现与运行状态见 milestones.md。
- 依据：[项目要求](project.md)、[系统架构](architecture.md)。
- 主要读者：负责执行开发任务的 agent。
- 用途：让 agent 根据简短的角色指示，自行找到职责、任务、依赖、可修改范围和验证方式。

**本文的阅读、检查、编码、验证、记录与交接要求均面向 agent 执行，不要求成员本人阅读全部文档、使用固定提示词、手动填写交接表或逐项执行开发检查。** 下文 A、B、C 默认表示承担相应角色的 agent。用户保留已经明确要求的规范修改审批，以及确需人工决定的事项。

本文件属于受保护的项目规范。**修改、删除、重命名或移动本文件，必须事先获得人工对具体变更的明确批准。** 普通代码协作不构成修改分工、需求或契约的授权；仅 `docx/milestones.md` 可按约定更新日常进度，不能借此重新分配冻结的职责。

## 1. 从简短指示识别角色并自主开工

A、B、C 是稳定的项目角色，不随当前对话用户变化。成员的姓名与 GitHub 账号尚未在本文件中绑定，agent 不得从用户名、分支名、当前目录或其他文档中的“当前用户”等措辞推断自己的角色。

用户说“我会完成 B 的任务”“我负责 B”或其他含义明确的简短表述，就足以指定 B 角色。agent 应直接读取 B 的职责并推进当前允许开展的工作，不要求用户再提供姓名、账号、职责复述、文件清单或完整开工提示词。

已有明确身份时，后续沿用，直到用户更改；不用每轮重复确认。只有结合当前授权上下文仍无法区分角色，或用户指示确实冲突时，才简短询问，不能仅凭用户名或目录猜测。

agent 自行完成以下准备，不把它们变成用户需要填写的步骤：

1. 读取根目录 `AGENTS.md`，核对项目要求、架构、本文件、当前里程碑与仓库状态。
2. 用户已经指定具体任务时，按该任务执行；只指定角色时，从里程碑中定位该角色当前未完成、依赖就绪的任务。
3. 里程碑没有具体条目时，在当前阶段和已批准职责内，选择可独立开展的最小任务并说明依据；不能因此要求用户重新拆解文档里已有的工作，也不能跳过当前阶段限制直接启动全部开发。
4. 按所选任务读取数据契约、接口契约、环境与 Git 规范，确定输入、修改范围、交付物和验证方式，不要求每次重复通读无关内容。
5. 简要报告自己的角色、本次工作和“下一步计划”，随后在已授权范围直接执行。这是进展说明，不是额外的开工审批。

文档或依赖尚未建立时，agent 先检查仓库中实际可用的内容，说明缺口并继续不依赖该缺口的已授权工作；只有无法从已有资料获得、且确实阻止继续执行的信息，才请求用户补充。不能把规划路径当作可用程序，也不能自行改写受保护文档补齐约定。

普通实现、必要验证、运行说明和交接记录由 agent 完成，不为代码细节反复请求人工确认，也不把可自行完成的开发步骤转交给成员手动操作。角色身份不自动授权扩展功能、改写规范或执行未安排的其他角色任务。

## 2. 分工总览

| 角色 | 原计划工作量 | 负责形成的能力 | 主要交付对象 |
| --- | --- | --- | --- |
| A | 35% | 来源、爬虫、清洗、标准数据、Hadoop/HDFS/YARN 环境与上传、数据库结构与导入、可调用的数据查询模块。 | B 获取标准输入和计算环境入口，C 获取数据查询能力，各角色 agent 共用样本与质量说明。 |
| B | 35% | MapReduce 与 Spark SQL 作业、同批统计对账、分析结论、可调用的偏好推荐模块。 | A 获取待导入统计，C 获取推荐能力与图表所需结果，各角色 agent 获取分析与作业依据。 |
| C | 30% | Vue/ECharts 页面、Flask 应用与 HTTP 接口组织、网页运行部署、模块接入及联调协调。 | 用户获得网页系统，A/B 获得接入反馈，各角色 agent 共用可复现的演示流程。 |

占比是原计划的工作量估计，不是对成员本人新增的操作要求，也不表示 C 需要替其他角色补齐所有缺失模块。各角色 agent 对自己的代码、必要检查、运行说明和问题修复负责；系统测试、报告、PPT 与演示材料由相关 agent 协同准备。

**环境与计算归属已按验收方案确定：A 负责 Linux Java、Hadoop/HDFS/YARN 的配置启停和 HDFS 上传；B 负责 MapReduce/Spark 作业与同批对账；C 负责网页运行部署。** 具体版本、入口与复现方式查 `docx/environment.md`，不在此复制另一套环境规范，也不将集成所需全部环境默认转交给 C。

## 3. A：爬虫、清洗、数据库与查询

### 3.1 工作范围

- 在既定项目范围内自主选择、验证和调整主要及备用来源，记录实际覆盖、可获取字段、来源时间与使用限制，不需要等待其他成员逐个指定网站。
- 编写来源爬虫，保留原始数据与失败记录，处理可预见的来源变化。
- 统一清洗、去重、行政区、等级与缺失值处理，生成带批次记录的标准 CSV 和质量统计。
- 按数据契约实现数据库结构、标准数据与已校验分析结果的导入，保证重跑不会无提示地累计重复景点。
- 在 `backend/app/repositories/` 提供列表、详情、筛选候选、统计结果与数据说明的查询能力，供 C 和推荐流程调用。
- 建立并验证 Linux Java、Hadoop/HDFS/YARN 环境与配置启停入口，交付给 B 复用，不要求 B 另建冲突的集群配置。
- 提供符合数据契约的标准输入，负责 HDFS 批次上传、读回摘要与完整性验证，不覆盖同名已发布批次。

### 3.2 交付与完成条件

| 交付 | 完成条件 |
| --- | --- |
| 来源记录与采集程序 | 能取得真实样本；来源、采集时间、覆盖与失败情况可追溯。 |
| 标准快照与质量说明 | 可由原始数据重新生成，包含数量核对及缺失说明，B 能按契约读取。 |
| 共同样本 | 各角色 agent 可以使用同一批样本；真实来源数据与构造的测试记录明确区分。 |
| 数据库结构与导入 | C 能按说明初始化并使用约定样本；批次与统计一致，重复导入行为明确。 |
| 查询模块 | C 可调用并接入 HTTP 接口；候选读取能支持 B 的推荐需要，不要求 C 重写数据库查询。 |
| Hadoop/HDFS/YARN 与上传入口 | B 能复用实际配置和启停入口；HDFS 读写与 YARN 服务检查有证据，正式输入与标准快照字节摘要一致，失败的 staging 不计作可用批次。 |

A 负责来源解析、清洗规则、数据内容、Hadoop 服务与上传、数据库结构与查询缺陷的修复。价格和类型的可用程度应由真实数据说明，不能为满足页面或算法需要补造资料；改变已批准的数据口径仍需人工批准。

## 4. B：分析与推荐

### 4.1 工作范围

- 在统一环境与输入契约具备后，用 Spark SQL 处理同一批 HDFS 标准输入，完成需求规定的统计与分析。
- 在 `analysis/mapreduce/` 实现项目 Hadoop Streaming 作业、运行入口和结果转换，在实际 YARN 上处理该批 HDFS 输入，复用 A 的配置与服务。
- 提供统计结果及有效样本、缺失情况、批次信息，提出有数字依据的分析结论。
- 对 MapReduce 与 Spark SQL 的重叠统计逐项核对，保留各自的实际运行证据，确认对外发布的结果不重复累加；不能用一个引擎的结果冒充另一个引擎。
- 在 `backend/app/services/` 实现可调用的推荐函数，负责匹配、排序与推荐理由，通过约定输入接收偏好和候选数据。
- 与 A 明确候选读取需求，与 C 明确推荐函数接入方式；不在推荐函数内另建数据库连接、爬虫或 HTTP 服务。
- 根据实际数据设计和验证排序方案。权重与最终规则尚未确定，不能预填效果指标或宣称已经验证；可选聚类不阻塞最小推荐功能。

### 4.2 交付与完成条件

| 交付 | 完成条件 |
| --- | --- |
| Spark SQL 程序 | 对约定样本能实际运行，输入、输出和运行方式可复现。 |
| MapReduce 作业与对账 | 项目作业在实际 YARN 运行，保留作业标识、输入输出和计数依据；与 Spark SQL 使用相同批次及摘要，重叠统计按契约一致。构造样本与真实项目运行分别记录。 |
| 统计结果 | A 能按数据契约导入，C 能按接口契约使用，能够核对数据批次与数量。 |
| 分析结论 | 满足项目要求，有对应统计依据、样本范围与口径说明。 |
| 推荐模块 | C 可直接调用；偏好实际影响结果，理由与规则一致，不要求 C 重写算法。 |
| 推荐验证与说明 | 覆盖预算边界、未知价格、无结果和无效输入等必要情形，说明规则与已知局限。 |

B 负责统计计算、推荐规则与理由生成的缺陷修复。原始字段或清洗存在问题时，与 A 核对并按批次流程更新，不能在分析中私自修改标准快照或为对账成功改写结果。

## 5. C：网页、接口组织与系统接入

### 5.1 工作范围

- 使用 Vue、ECharts 实现需求中的分析、查询、推荐和数据说明，页面控制在项目约定范围内。
- 实现 Flask 应用入口、HTTP 路由、参数校验和响应组织，调用 A 的查询模块与 B 的推荐模块。
- 接入数据库中已校验的统计结果，完成地图行政区匹配与展示，并向 A 反馈名称、代码或缺失方面的问题。
- 落实加载、空结果与失败反馈，不使用固定演示数值掩盖数据或接口故障。
- 组织模块接入与联调，按共同样本检查数据、分析、接口与页面是否一致，整理网站启动与演示步骤。
- 按已验收环境方案准备 Node/npm、Vue/ECharts、Flask/WSGI 与网页部署接入；这一责任不等于接管 A 的 Hadoop 服务或 B 的计算作业。

### 5.2 交付与完成条件

| 交付 | 完成条件 |
| --- | --- |
| Flask 应用与接口 | 按接口契约处理请求，正确调用查询与推荐模块，有明确的参数与依赖失败反馈。 |
| 网页与图表 | 从实际接口动态取得结果，图表和列表对应同一批数据，字段说明与数据范围准确。 |
| 推荐页面 | 用户可以输入偏好、查看结果与理由，无结果时反馈清楚。 |
| 联调记录 | 问题可定位到输入、计算、查询、接口或页面，标明责任模块与复现方式。 |
| 启动与演示流程 | 接手的 agent 能按统一环境说明执行启动检查，交付可复现的查询、统计和推荐演示步骤。 |

C 负责路由、参数传递、响应组织、页面与接入缺陷的修复。发现上游未完成或返回错误时，应交回相应负责人处理，不在路由或前端复制 SQL、清洗、统计或推荐算法来绕过问题。

| `tests/` | 各模块负责人 | A/B/C 各自维护必要检查；C 协调联调，相关成员修复自己模块的问题。 |

| 规范文档、环境配置样例、Git 规则与 PR 模板等约定入口 | 人工批准后按授权维护 | 不能因承担某模块而自行修改公共约定；具体规则由 AGENTS 与 Git 规范落实。 |

`data/metadata/` 中的批次、来源、清洗和计算记录由对应产出者维护；跨阶段记录使用同一批次标识。共享目录不能成为无人负责的区域，也不能被理解为任何 agent 可随意重写。

## 7. agent 生成交接记录并验证接入

| 交接方向 | 交付内容 | 接收方 agent 如何验证 |
| --- | --- | --- |
| A → B | 标准样本、批次与字段说明、质量情况、已验证的 HDFS 输入及配套元数据、Hadoop 配置与启停入口。 | B 能核对字段、数量和摘要，访问正式批次路径并复用实际 HDFS/YARN 环境；不读取 staging。 |
| A → C | 数据库初始化与导入能力、查询模块、共同样本和数据范围说明。 | C 能用约定样本调用查询，无需重新编写数据访问逻辑。 |
| B → A | 待导入的已校验统计、批次、指标与口径。 | A 能按契约导入；统计与标准数据及 MapReduce 重叠结果可核对。 |
| B → C | 可调用推荐函数、规则说明、示例输入输出及图表所需结果说明。 | C 能按接口契约接入，必要边界表现明确。 |
| C → A/B | 接入反馈、复现步骤、实际与预期差异、涉及的数据批次。 | 对应负责人能复现并修复，不以“前端有问题”等笼统描述代替定位信息。 |
| A → 各角色 agent | Hadoop/HDFS/YARN 配置、启停与上传入口及实际服务检查材料。 | 接手的 agent 能复用所需服务、定位正式输入并检查摘要；安装完成不冒充计算作业通过。 |
| B → 各角色 agent | MapReduce/Spark 的运行入口、结果转换、作业证据与同批对账材料。 | 接手的 agent 能找到各引擎实际输入输出，区分构造样本与真实项目结果。 |

交付 agent 根据实际产物和运行结果自动整理以下信息，供接收方 agent 读取，不要求成员本人填写或签收：

1. 本次交付的能力、文件路径及适用数据批次；有提交或 PR 时提供对应标识。
2. 使用入口、依赖、必要输入及预期输出，不暴露密钥或本机私有配置。
3. 实际完成的验证及结果，尚未验证的内容、已知限制与阻塞项。
4. 接收方下一步需要做什么，哪些问题仍由交付方负责。

接收方 agent 能够读取产物与入口后，应自行完成相应接入检查并记录实际结果；相关代码已具备时，可以直接执行可复现的联调验证，不以人工阅读文档或手动签收作为开工条件。

文件已生成不等于集成已经通过。只完成自测、尚未执行接入验证时，如实标记“待接入验证”，继续其他可独立完成的任务；没有实际验证或对方确认，不能替其他 agent 宣称通过，也不能声称已完成跨会话沟通。

## 8. 跨模块修改与阻塞处理

- 各自维护责任模块，在已批准任务范围内完成必要实现与修复。普通代码修改无需套用规范文档的人工审批要求。
- 需要改动其他角色模块时，先说明原因、影响、涉及文件与验证方式，通过已获准的协作渠道与相关角色 agent 对齐后进行最小必要修改；不能借修复一个问题重构他人整块代码，也不能要求用户充当日常代码信息的搬运者。
- 数据字段、接口约定、职责或功能范围需要变化时，提出具体方案，**先获得人工明确批准，再修改受保护规范及对应实现**。不能以两个 agent 已经达成一致代替人工批准。
- 修改前检查仓库与未提交内容，不覆盖、不回退其他成员或用户的工作；共享文件出现冲突时按 Git 规范处理。
- 依赖未交付时，记录缺少什么、需要谁提供以及对当前任务的影响。可以继续独立任务或使用明确标记的测试替身，但测试替身不算真实集成完成。
- 进度统一更新到 `docx/milestones.md`，不再新增另一份共享进度账。不能把“已提出建议”记录为“已批准”，也不能通过进度记录悄悄变更负责人。
- 跨会话沟通使用已经获准的协作渠道；没有实际发出或收到确认时，不宣称已通知其他成员或其 agent。

遇到问题时按实际责任定位：数据内容和查询由 A 排查；统计与推荐由 B 排查；接口组织与页面由 C 排查；无法定位时共同复现，而不是直接将所有问题交给 C。

## 9. 共同任务与当前边界

- 各角色 agent 根据自己部分的真实方法、运行结果、图表依据与局限生成可整合材料；文案统稿不转移实现与证据责任，不要求成员本人手动补写 agent 已能生成的内容。
- C 对应的 agent 整理完整演示步骤，A/B 对应的 agent 分别准备数据与算法环节的说明，并协同验证样本流程和网站演示。
- 测试、报告、PPT 与答辩按里程碑中的共同任务和实际阶段安排，不在本文件编造尚未确定的日期。
- 开工、进展和交接汇报应清楚说明结果、限制与“下一步计划”，不能只汇报正在做什么。
- 文档准备阶段按用户指定的范围逐份创建文件，全部文档完成后统一提交一次文档 PR。当前所处阶段与可执行任务由用户最新指示及里程碑确定，不在本文件固化某次会话的临时进度，也不因用户只指定角色就跳过阶段限制。

配套规范已建立。数据字段与统计口径以 `docx/data-contract.md` 为准，模块调用与 HTTP 约定以 `docx/api-contract.md` 为准，版本、环境任务和运行方式按 `docx/environment.md` 执行；每次开始或恢复开发先按 AGENTS 与 `docx/git-workflow.md` 检查并同步远端。缺少实现或依赖时先说明具体缺口，不自行编造共享约定。
