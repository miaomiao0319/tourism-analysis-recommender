## 2. 项目目标与研究问题

围绕旅游景点选择这一实际场景，从适合采集的网页获取景点资料，经过清洗、存储与大数据处理，提供可视化分析、景点查询和基于偏好的推荐功能。

目标用户是希望根据目的地、门票预算和兴趣寻找景点的出游者。项目需要同时形成可运行的网站和有数据依据的分析结论，展示从网页采集到结果应用的完整过程。

核心研究问题如下：

1. 在实际采集范围内，各城市或地区的景点数量与景区等级分布有何差异？
2. 在门票价格可获取的样本中，不同地区、等级或类型的价格分布有何特点？
3. 根据用户选择的城市、门票预算和兴趣，可以推荐哪些景点，为什么推荐？

分析结论必须限定在数据实际覆盖的地区、来源和采集时间内。景点数量不直接代表游客热度，相关关系也不能直接表述为因果关系。

### 2.1 数据覆盖与时间范围（已确认）

- 以中国全国范围为基础覆盖目标，尽可能收集各地区景点资料；实际覆盖地区、缺口和记录数量必须如实说明，不得将全国目标表述为已经采集了全国全部景点。
- 在数据来源、处理口径与实现条件可行时，可以扩展到全球景点。全球覆盖是可行时的扩展，不作为全国范围最小交付的前置条件；涉及跨国资料时，需要说明国家或地区、币种及等级体系的差异，不能直接混用。
- 数据时间口径截至 **2026 年 10 月**。来源资料的发布时间或更新时间与实际采集时间应分别记录，以实际可取得的信息为准，不得声称取得了尚未发生或尚未发布的信息，也不能将采集当天的票价冒充历史票价。
- 2026 年 10 月是数据时间范围，不是项目交付截止日期；项目截止日期目前未定。
- 课程没有最低数据量要求。在来源适合使用、数据质量与实际资源允许的范围内，尽可能扩大有效数据量和地区覆盖；以去重后的景点数量和覆盖情况说明成果，不用重复记录或低质量数据凑量。

## 4. 最小交付范围

### 4.1 数据采集与清洗

必须完成以下内容：

- 由成员 A 在既定项目范围和采集约定内自主选择、验证与调整主要数据源及备用来源或备用数据方案，登记实际来源清单；目前尚未指定具体网站或数据集。
- 记录来源页面、采集时间、覆盖范围、可获取字段，以及采集和数据再分发的依据或限制。
- 编写能够重新运行的采集程序，保留原始结果，生成清洗后的标准数据。
- 完成去重、缺失值标记、格式统一、行政区与景区等级整理，并记录处理规则和处理前后数量。
- 将标准数据导出为 CSV，导入 MySQL，并提供大数据处理所需的 HDFS 输入。
- 对采集和导入失败给出可检查的记录，避免无提示地丢弃数据或重复写入。

采集范围以可正常访问、适合本项目使用的公开资料为起点。遇到登录、访问控制、验证码或明确的采集限制时，不得将绕过这些限制作为项目实现方案。公开可访问不等于可以任意采集或重新发布，相关依据需要登记。

### 4.2 数据字段与质量底线

| 信息 | 最小要求 |
| --- | --- |
| 景点名称 | 核心信息；缺失记录不得直接作为正常景点参与展示。 |
| 所属城市、上级地区 | 尽可能标准化，支持地区汇总；无法识别的记录单列，并计入质量说明。 |
| 景区等级 | 优先来自可追溯的名录或页面；未知与无等级不能混为一类。 |
| 门票价格 | 尽力采集；注明价格含义与来源，允许未知，不能为凑齐字段编造。 |
| 景点类型 | 支持兴趣推荐所需的分类；允许基于可解释的规则整理，保留分类依据。 |
| 数据来源、采集时间 | 能够追溯展示与分析结果。 |

游客评分、评论、开放时间、经纬度和图片属于可选增强字段，不是最小版本的前置条件。具体数据库字段、单位、空值编码和去重主键，由 `docx/data-contract.md` 统一定义，本文件不另建一套字段标准。

质量处理必须遵循以下底线：

- 免费、价格未知、价格区间和数值为零不能未经判断相互替代。
- 不同票种、套票、起步价和完整门票价格不能未经说明直接混合比较。
- 不能将重复出现于不同网页的同一景点简单当作多个景点统计。
- 价格分析需报告有效样本数和缺失情况；字段不可用时，不得生成虚假的价格结论。
- 演示样例、测试数据和真实采集数据需要明确区分，不得用生成数据冒充采集成果。

门票价格和景点类型的可用覆盖率、具体价格比较口径，在后续实践过程中根据实际数据评估确定，目前不预设覆盖率门槛。确定后的口径按 `docx/data-contract.md` 统一记录，修改受保护文档仍须人工明确批准。

如果价格覆盖率或景点类型质量不足以支撑分析和推荐，应提出补充或缩减方案，由人工确认；不能静默取消对应需求。

### 4.3 Hadoop/HDFS 与 MapReduce

HDFS 必须存储项目实际使用的景点输入数据，MapReduce 必须读取这些输入并产生与景点分析有关的输出，结果可检查、可复现。

最小 MapReduce 任务为：

- 按城市统计清洗后景点数量。
- 按景区等级统计清洗后景点数量，未知等级单列。

两项统计可以在一个或多个作业中实现，不要求为增加作业数量拆分程序。应保留输入输出位置、运行命令、执行记录和结果样本，并用同一批小样本进行独立统计核对。

部署至少需要能真实运行 HDFS 和项目 MapReduce 作业。已验收环境方案采用单机伪分布式 HDFS/YARN，具体要求见 `docx/environment.md`；不得将伪分布式演示描述为多台机器的实际并行性能验证。

### 4.4 Spark SQL 与分析结论

Spark SQL 必须在同一版标准数据上开展统计，至少覆盖：

- 地区或城市的景点数量及排序。
- 景区等级总体分布，以及不同地区的等级构成。
- 有效门票价格的分布和分组比较，注明价格口径与有效样本范围。
- 数据质量概况，包括总记录数、关键字段缺失情况和主要清洗结果。

MapReduce 和 Spark SQL 统计口径重叠的结果，应在同一数据版本上对账。两个框架的使用记录都需要保留，不能用一个框架的结果冒充另一个框架的运行结果。

除图表外，至少形成 3 条有统计结果支持的分析结论，回答前述研究问题中的分布与差异问题。若样本不足，应如实说明，并经人工确认调整分析范围。

### 4.5 基于偏好的景点推荐

最小推荐方案采用可解释的条件匹配与排序，不要求先获得用户历史评分，也不要求训练复杂模型。

- 输入支持城市或地区、门票预算和景点兴趣；具体选项与参数格式在接口契约中确定。
- 本项目将“预算”定义为**单个景点的门票预算上限**，不包含交通、住宿、餐饮或多日行程费用，页面必须说明这一点。
- 推荐先满足用户明确选择的约束，再按可解释的规则排序；返回景点信息和推荐理由。
- 用户设置门票预算时，价格未知或无法按统一口径比较的景点，不得宣称符合该预算。无有效匹配时返回清楚的说明，不得自动放宽条件而不告知用户。
- 预算允许为零，用于匹配已经确认免费的景点；负数等无效输入需要校验。
- 推荐规则、排序依据和无结果处理必须有说明；不能将规则分数表述为经过训练得到的准确率或真实用户满意度。

验证至少覆盖正常匹配、预算临界值、免费与未知价格的区别、无匹配结果和无效输入。推荐效果以条件符合程度、理由一致性和演示案例验证为基础；没有真实评价数据时，不编造算法准确率。

### 4.6 网站与展示

最小网站提供以下能力，允许将相近功能合并在同一页面：

1. 分析总览：景点分布地图、城市景点数量排行榜、等级统计和有效价格统计。
2. 景点查询：按名称搜索，按地区、等级、价格或类型筛选，并查看来源等基本信息。
3. 偏好推荐：填写偏好，查看推荐结果和推荐理由。
4. 数据说明：说明采集范围、数据更新时间、字段缺失和价格适用范围，可与其他页面合并。

地图优先按省份或城市汇总展示，缺少景点经纬度不应阻断最小版本。地图资源、行政区匹配和数据覆盖范围需要说明；精确景点点位地图属于可选增强。

没有真实游客热度指标时，排行榜名称应使用“景点数量排行榜”等准确表述。网页需具备加载、空结果和失败反馈，不能只展示预先固定的截图。

## 5. 技术范围与处理流程

| 环节 | 计划技术与作用 |
| --- | --- |
| 网页采集 | Python、Scrapy，获取真实景点资料。 |
| 清洗与导出 | Pandas，整理标准数据和质量记录。 |
| 分布式文件存储 | Hadoop/HDFS，保存实际计算输入与输出。 |
| 批量统计 | MapReduce，执行项目景点统计作业。 |
| 多维分析 | Spark SQL，进行分组、分布与比较分析。 |
| 业务数据与结果存储 | MySQL，支持景点查询与结果读取。 |
| 接口服务 | Flask，向页面提供查询、分析与推荐接口。 |
| 页面与可视化 | Vue、ECharts，展示分析、查询与推荐功能。 |

总体流程为：网页采集 → 原始数据留存 → 清洗与标准化 → HDFS 输入及计算 → MapReduce/Spark SQL 统计 → MySQL 中的业务数据与分析结果 → Flask 接口 → Vue 页面。推荐模块使用同一版标准景点数据，向接口提供推荐结果。

清洗后的 CSV、HDFS 输入、MySQL 数据和分析结果应能对应到同一数据版本，避免各成员使用不同批次数据而无法核对。

大数据分析采用离线执行、结果供网站读取的方式即可；最小版本不要求每次打开网页都启动 Spark 或 MapReduce。详细目录、模块调用和数据同步方式见 `docx/architecture.md`。

具体 Python、Java、Hadoop、Spark、MySQL、Node.js 版本、部署平台与运行方式见已验收的 `docx/environment.md`，实际安装兼容性仍须运行验证。最小交付为本机网页系统，构建页面由 Flask 同源提供服务；公网部署尚未确定，不将其作为默认承诺。本文件不复制环境版本表。

## 6. 可选增强与范围边界

在最小版本跑通、数据质量满足条件后，可以提出以下增强：

- 特征适合时使用 K-Means 聚类，并说明特征选择、处理方式及聚类的业务含义。
- 提高价格、类型、开放时间等字段覆盖率。
- 在资源条件允许时增加精确点位地图、推荐解释或排序比较。

可选增强不得阻塞最小版本，也不能替代必做的 Hadoop/HDFS、MapReduce、Spark SQL 和偏好推荐。引入影响共享数据、接口或交付范围的增强，应先获得人工批准并同步相关契约。

当前最小版本不包含用户注册登录、用户画像与行为追踪、协同过滤、实时票价承诺、购票支付、路线规划和商业化服务。增加这些功能需要单独确认范围与成本。

## 7. 三人协作与交付边界

| 成员 | 原计划占比 | 主要责任与交付 |
| --- | --- | --- |
| A | 35% | 自主选择与验证主要及备用数据源，完成爬虫、清洗、CSV、数据库设计与导入、Hadoop/HDFS/YARN 环境与上传；向计算与网站提供可使用的数据和查询能力。 |
| B | 35% | MapReduce 与 Spark SQL 分析、统计结果、偏好推荐与算法说明；负责计算作业、同批对账及分析结论。 |
| C | 30% | Vue/ECharts 页面、Flask 接口组织、模块接入、网站联调与演示。 |

占比是初步工作量估计，不是验收结果。环境与计算任务已按验收方案同步到 `docx/roles.md`：A 负责 Hadoop/HDFS/YARN 与上传，B 负责 MapReduce/Spark，C 负责网页运行部署；具体入口、交接与验证见分工和环境规范，不因 C 协调集成而转移上游职责。

为减轻 C 的压力，A 应交付可调用的数据查询模块，B 应交付可调用的推荐模块及约定的统计结果。HTTP 路由、共享配置和各代码目录的归属在分工与架构文档中明确，避免多个成员重复实现。

系统测试、实验报告、答辩 PPT 和项目演示由三人共同完成。数据和接口契约确定后，各成员使用共同样例进行开发，不等待全量采集结束才开始联调。

## 9. 验收标准

| 验收项 | 通过条件 |
| --- | --- |
| 数据来源 | 有真实样本、来源与时间记录，按全国目标说明实际覆盖与缺口；如有全球扩展，单独说明其范围与口径；记录采集、再分发限制。 |
| 清洗与存储 | 原始与标准数据可区分；清洗规则和记录数可核对；CSV 与 MySQL 中的标准数据一致。 |
| HDFS | 项目真实数据已写入并能够读取，有明确路径和操作记录。 |
| MapReduce | 能对景点数据运行规定统计，输出可检查，并与小样本的独立统计一致。 |
| Spark SQL | 完成规定分析；与 MapReduce 重叠的统计在相同数据版本上对账。 |
| 分析结论 | 至少 3 条有数字依据的结论，清楚限定样本和价格口径，不夸大热度或因果关系。 |
| 推荐 | 偏好实际影响结果；满足已选约束；理由与规则一致；未知价格及无结果情形处理正确。 |
| 网站联调 | 能从数据与接口动态展示地图、图表、景点查询和推荐；具备必要的空状态与错误反馈。 |
| 可复现性 | 按统一环境说明，能够从约定样例完成导入、计算、接口启动和网页演示。 |
| 交付完整性 | 代码、文档、运行记录、报告、PPT 和演示流程相互对应，没有用静态截图代替未实现的功能。 |

课程已确认没有最低数据量要求；项目以尽可能增加有效景点数量和地区覆盖为采集目标，并如实报告结果。响应时间、准确率或集群节点数目前没有已确认的量化要求，不得将自行设定的数值表述为课程指标。后续确需补充项目量化目标时，经人工批准记录。
